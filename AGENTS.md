# Workspace conventions

- Keep shared assets, configuration, outputs and scripts at the workspace root. Put each scene implementation in `examples/<name>/`; reusable Python utilities belong in `src/mujoco_tools/`.
- Keep the generated canonical scene at `examples/<name>/scene.xml`. Keep new raw collection datasets in `outputs/datasets/<name>/run_<timestamp>/`, or the explicit `--output` directory. Each raw episode must have its own `episode_<seed>/` subdirectory containing same-stem HDF5, YAML, XML and a single head-camera MP4. The ten-episode fixed-position batch is `outputs/datasets/insert_plug/test/`. Store execution results and diagnostics in HDF5 metadata rather than separate JSON, PNG or plan files. Store `model_path` and `execution_result.model` as the XML filename relative to the episode directory so the batch can be moved together.
- The current task is `insert_plug`. Expert targets and synchronized RGB-D/state/action recording both default to 10 Hz, with each command held for 100 ms and physics at 1 kHz. No hidden higher-rate target interpolation is used. Distinguish this aligned timing from legacy 50 Hz control / 10 or 15 Hz recording. Fixed holder positions are the default; randomization must be requested.
- The 100-episode grid batch uses the vetted `config/insert_plug_positions.yaml`: ten fixed layout pairs, two-centimetre grid steps, ten episodes per pair, both expert control and recording at 10 Hz with depth. Raw groups are `outputs/datasets/insert_plug/pos0` through `pos9`, with global episode numbers 0 through 99. Its merged local LeRobot dataset belongs at `outputs/datasets/insert_plug/lerobot/` and follows the official LeRobot directory format rather than the four-file raw episode layout. The preceding 100-episode 50 Hz-control batch and its derived LeRobot dataset were replaced and deleted at the user’s request. The current aligned 10 Hz batch passed all 100 physical action replays with zero contact violations; preserve it and the unrelated `test/` and historical records. Preserve new raw records and metric depth during conversion.
- Keep other explicitly requested images, dual-view videos and plan exports under `outputs/<name>/`, separate from dataset directories. Preserve recordings, user STL files and reusable assets during routine cleanup; remove obsolete generated previews and diagnostics when authorized.
- Use temporary directories for one-off verification. If results must remain for inspection, put them in `outputs/_checks/`; never leave migration reports, diagnostic JSON files, or test screenshots at the root.
- Remove your disposable verification outputs when work finishes. `scripts/cleanup_outputs.py --apply` additionally enforces the configured age policy for `outputs/_checks/`.
- Keep environment and dependency configuration at the root; use the shared Conda environment `mujoco`.
- LeRobot conversion uses the isolated `lerobot` Conda environment with its own root-level environment/lock files. Do not change simulator dependencies to satisfy LeRobot's Python or PyTorch requirements.
- Trained-policy deployment uses the isolated `mujoco_policy` Conda environment and the local `third_party/lerobot` fork. The scene-independent ACT adapter is `src/mujoco_tools/lerobot_policy.py`; task execution is `examples/insert_plug/rollout.py`, configured by `config/insert_plug_policy.yaml`. Preserve checkpoint files and their saved normalization statistics. Evaluation outputs belong under `outputs/insert_plug/rollouts/`, never in training datasets. A functioning inference loop does not imply task success: report physical success, contact violations and timeouts separately. Keep 10 Hz held actions / 1 kHz physics; do not silently clip model actions or substitute expert/planner corrections.
- User-requested full policy test batches belong under `outputs/test/<training_run>/`, alongside `outputs/train/`, grouped by `pos0` through `pos9`. Evaluate ten fresh episodes per position with seeds 0–99 unless requested otherwise; preserve actual per-episode reports, scene XML and dual-camera videos, plus batch summaries. Fixed-position repeated trials measure repeatability, not random-layout generalization. Do not overwrite existing test batches.
- The current ACT deployment configuration uses `n_action_steps=50`: execute 50 distinct 100 ms targets before predicting another chunk, retaining the trained `chunk_size=100`. The preceding 10-action batch and its diagnostics under `outputs/test/act_insert_plug_20261107_2044/` were explicitly deleted at the user's request and replaced by a fresh 50-action batch. Use the current batch metadata for results, and pass `--n-action-steps 50` to the batch audit script.
